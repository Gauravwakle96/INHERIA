# Judge demonstration guide

Open https://inheria.onrender.com/demo or choose Explore demo beside sign-in.
Free hosting may need about a minute to wake. Start interactive demo creates an
isolated workspace; no account, real company access or API key is needed.
The ShopEase sources are authored examples, not actual Wipro/client records.

## Main journey

1. **Connect — Rudransh:** inspect Connected sources. Thirteen documents cover
   project context, deployment, rollback, monitoring, recovery, decisions,
   dependencies, unresolved work and coordinator-only information. Upload your
   own authorised Markdown, PDF, DOCX, TXT or JSON to test fresh ingestion.
2. **Reconstruct:** run Investigate project. Inspect candidate responsibilities,
   missing backup ownership, unverified procedures, stale evidence and conflicting
   deployment decisions. Commit activity alone does not confirm responsibility.
3. **Verify:** open Project memory and inspect the exact quotation, document,
   location and version. Responsibility and procedure statements begin pending.
4. **Review:** review supported claims individually. In Decision intelligence,
   inspect rolling versus blue-green sources and explicitly choose the evidenced
   current authority. Rejected/uncertain material does not become verified truth.
   Switch to Gaurav to answer targeted knowledge questions; another authorised
   reviewer must assess his explanation.
5. **Handover:** generate the planned transition, inspect grouped ownership,
   procedures, decisions, dependencies, open work and risk questions. Approve the
   version, assign Gaurav's three responsibilities to Savinay with an appropriate
   backup, and create practical tasks. Approval permits sharing, not automatic
   acceptance or operational readiness.
6. **Continue — Savinay:** switch role in the topbar. Review the handover. Accept
   or reject each assignment. Complete practical explanations with selected
   evidence, safe staging boundaries and escalation. No cloud commands execute.
7. **Validate — Rudransh:** independently inspect submissions and each scenario
   criterion. Request revision for inadequate evidence, or record your assessment.
   Review the mandatory recovery-gap/follow-up check with appropriate citations.
   Closure is blocked until acceptance, practical review and required checks pass.

An actual restore test remains separate work unless a real authorised supervisor
provides its evidence. The demo validates understanding and recorded follow-up,
not AWS permissions or production recovery competence.

## Failure and permission demonstrations

- **Restricted source:** note the coordinator-only source as Rudransh; switch to
  Savinay and verify it disappears. Direct source access is also denied by the API.
- **Missing recovery knowledge:** inspect the missing restore-test record and
  backup owner. Explain next actions; do not invent recovery commands or outcomes.
- **Rejected transfer/task:** Savinay records a missing-information reason; a
  supervisor requests revision. Readiness remains incomplete.
- **Source change:** in Sources choose New version for an uploaded document.
  Impact shows affected claims/handovers/tasks. Investigate and review new
  evidence, reopen the active transition, regenerate, reapprove and reassess.
  Old quotes cannot be used as current truth.
- **Access readiness:** an incoming member requests knowledge access. A different
  authorised reviewer approves a source they can share or rejects with a reason.
  This does not grant GitHub, AWS or IAM permissions.
- **Team onboarding:** Rudransh creates an expiring invitation and shares its
  one-time link privately. New recipients choose a password; existing accounts
  authenticate without changing their role/password. No email is sent.

## Demonstration evidence

The local automated journey exercises real UI and API actions, including receipt
acceptance and independent review. Separate tests cover isolation, permission
denial, expired/reused invitations, interrupted investigations, ten source-change
recovery cases and five interruption positions. See verification.md for actual
run results, evaluation-report.md for measured extraction limits and feature-status.md
for unimplemented capabilities. Private production accounts are not modified by
the judge walkthrough.
